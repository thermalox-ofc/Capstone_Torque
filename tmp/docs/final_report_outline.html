1. Introduction

Torque Garage Public Prototype is a browser-based automotive service management system created to simulate the day-to-day workflow of a small independent repair shop. The project addresses a common problem described in the original project plan: many small auto shops still rely on fragmented paper records, disconnected spreadsheets, and manual communication, which increases the chance of scheduling conflicts, data loss, and inefficient inventory handling (Beo, Asmerom, & Hwang, 2025).

The original concept focused on building a practical web-based system that centralizes customer records, vehicle information, service tracking, scheduling, inventory monitoring, and loyalty-related workflow into one interface. As the project evolved, the implementation shifted toward a static but highly functional frontend prototype that still preserves the central goal of validating real repair-shop operations before full backend deployment (Beo, Asmerom, & Hwang, 2026a).

The current public version supports three roles: admin, operator, and customer. It demonstrates customer management, vehicle registration, appointment intake, operator assignment, work-order progression, inventory usage, invoice checkout, and a payment gate that prevents pickup completion until a work order has been marked paid. This final report integrates material from the team’s project plan, design report, source-code writeup, user guide, and earlier final-report draft into one detailed and comprehensive submission.

2. Process Overview

The team followed an iterative development process influenced by Agile and Scrum principles. According to the project design document, one-week sprint cycles were chosen because the team was small, the project requirements were likely to evolve, and incremental delivery allowed each feature area to be tested and corrected before additional complexity was added (Beo et al., 2026a). This approach aligned well with the staged nature of the application: login, customer management, vehicle tracking, appointments, operator workflow, and inventory management could each be developed as visible modules.

Approach

  • Begin with a browser-based prototype rather than a full-stack deployment so the team could validate interface and workflow decisions early.
  • Use seeded demo users and seeded records to support repeatable testing and immediate demonstrations.
  • Develop role-based visibility and workflow transitions in small increments rather than all at once.
  • Use testing feedback to tighten workflow gates, especially in scheduling, inventory deduction, and pickup completion.

Tools and Artifacts Used

  • HTML, CSS, and Vanilla JavaScript for interface, styling, and application logic
  • Browser localStorage for lightweight JSON-based persistence during the MVP phase
  • Git and GitHub for source control and collaboration
  • VS Code, shared formatting conventions, and project documentation artifacts from each course phase (Beo et al., 2026c)
  • Project Plan, Project Design, User Guide, Source Code deliverable, and prior Final Report draft as reference artifacts

3. Requirements Specification

Functional Requirements

The project design and plan consistently emphasized core service-desk functionality over advanced enterprise features. The final implemented prototype fulfills or simulates the following major functional requirements, derived from the team’s planning documents and refined through later implementation work (Beo et al., 2025; Beo et al., 2026a):

  • The system shall support login for admin, operator, and customer users.
  • The system shall enforce role-based access and limit features by user type.
  • The system shall allow admin users to create, view, edit, and delete customer records.
  • The system shall allow admin users to create, edit, and delete vehicle records linked to customers.
  • The system shall allow admin users to manage operator accounts.
  • The system shall allow customers and admin users to create appointments.
  • The system shall allow admin users to assign appointments to an operator and service bay.
  • The system shall create and track work orders linked to appointments.
  • The system shall allow operators to update work notes, mileage, diagnostic codes, and job status.
  • The system shall deduct inventory when materials are consumed by a work order.
  • The system shall allow invoice preparation with labor, inventory-based materials, and other charges.
  • The system shall require payment confirmation before admin can complete pickup.
  • The system shall let customers view customer-safe appointment and service updates.

Non-Functional Requirements

  • Performance: The interface should load quickly under normal browser use.
  • Usability: The system should be understandable to non-technical shop users and should work on desktop and mobile browsers.
  • Security: Passwords should be protected through hashing and sessions should expire after inactivity (Beo et al., 2026a).
  • Reliability: Data should persist after refresh in the browser environment.
  • Maintainability: The codebase should remain organized, documented, and modular enough to support future backend migration (Beo et al., 2026c).

Scope Adjustments

The project plan explicitly marked payment processing, multi-location support, advanced analytics, and SMS/email reminders as out of scope for the initial course delivery (Beo et al., 2025). The final build remained consistent with that decision in one important way: it supports invoice and payment status logic inside the prototype, but it does not perform live payment transactions or external billing integration.

4. Project Design

Architecture and Implementation

The earlier design document proposed React, Node.js, MySQL, JWT-based authentication, and cloud hosting for a fuller implementation path (Beo et al., 2026a). The final course implementation deliberately simplified that architecture into a static frontend system using HTML, CSS, JavaScript, and localStorage. This change reduced infrastructure complexity and made it easier to deliver a polished working prototype in the available time.

The implementation now follows a browser-side architecture:

  • index.html: Defines the UI structure, forms, dashboard panels, and role-based sections.
  • style.css: Defines layout grids, panel styling, responsive behavior, validation styling, and dashboard presentation.
  • script.js: Handles login logic, state persistence, rendering, validation, scheduling, inventory deduction, invoice checkout, and payment gating.

How the System Works

  1. A user logs in with the appropriate role and seeded credential set.
  2. The system loads and normalizes data from localStorage.
  3. Admin manages customers, operators, vehicles, inventory, and appointments.
  4. Appointments are assigned to an operator and bay, which creates a linked work order.
  5. Operators update the work order and record materials used by SKU.
  6. Admin verifies completed work and moves the job to ready-for-pickup.
  7. Admin prepares an invoice, confirms payment, and only then completes pickup.

Data Model Summary

The design report and Phase I source-code document described a localStorage-backed data model that mirrors the structure of a future relational system (Beo et al., 2026a; Beo et al., 2026c). The final prototype stores JSON collections for users, customers, vehicles, appointments, work orders, work-order parts, inventory, and loyalty records. This structure preserves the project’s original conceptual model while keeping the browser-based MVP lightweight.

Pseudocode and Algorithm References

The pseudocode patterns that influenced the final implementation came from the Phase I source-code document, especially in the persistence layer, VIN validation logic, and customer and vehicle validation examples (Beo et al., 2026c). While the current code has evolved beyond that initial phase, the final report still cites those pseudocode-oriented materials because they document the team’s original implementation logic and validation structure.

5. Project Evaluation

Testing Strategy

Testing focused on user-facing behavior, validation rules, role-based visibility, workflow transitions, and persistence. The team’s earlier documents already emphasized manual functional testing and validation of localStorage behavior, login behavior, CRUD operations, VIN checks, and required-field handling (Beo et al., 2026c). The final system extended that strategy to include appointment conflict handling, operator assignment rules, inventory deduction by SKU, and invoice payment gating.

Test Plan and Results Summary

Category Representative Result
Authentication Admin, operator, and customer login succeed with valid seeded credentials; invalid credentials are rejected.
Role-Based Access Customer view is restricted to portal data; operator view is restricted to service operations.
Customer and Vehicle CRUD Create, update, and delete behaviors function correctly with persistence after refresh.
Validation VIN checks, required fields, positive mileage, and appointment time rules behave as expected.
Scheduling Bay conflicts and operator double-booking are surfaced and reassignment is supported.
Inventory Materials logged by SKU deduct inventory correctly and can be reflected in work-order/invoice data.
Checkout Pickup completion is blocked until invoice payment is recorded through admin password confirmation.

Validation Using Seeded Data

Seeded data remained a major validation asset throughout the project. Known-valid credentials, VINs, customer emails, and inventory SKUs allowed the team to start from trusted values and then alter one rule at a time. This was especially helpful when validating invalid VIN length, invalid email format, duplicate scheduling, and later invoice-and-pickup state behavior.

6. Design and Alternate Designs

Several design changes were made after testing and review. These changes were not arbitrary refinements; they corrected workflow issues that only became clear once the system was exercised through realistic user scenarios.

  • The original higher-complexity React/Node/MySQL architecture was replaced by a simpler HTML/CSS/JavaScript/localStorage architecture to improve feasibility and deliver a stable MVP (Beo et al., 2026a).
  • Logout behavior was improved so it feels immediate to users while background cleanup runs afterward.
  • Operator management was added to the admin workflow instead of relying on a single static operator record.
  • Scheduling rules were tightened so same-time conflicts for operator and bay occupancy are detected and corrected.
  • Work-order inventory logging changed from name-based entry to SKU-based entry for better consistency with inventory records.
  • An invoice checkout panel was added because testing exposed the need to verify payment before completing pickup.

Alternate designs considered or originally planned included a true backend API, database-backed persistence, real notifications, and cloud deployment. Those remain valuable future directions, but the course prototype benefited more from reliable visible workflow behavior than from unfinished infrastructure.

8. Discussion

Lessons Learned

  • Working through visible workflows exposed design problems faster than abstract planning alone.
  • Seeded data made validation more disciplined because the team could compare valid and invalid cases directly.
  • Role-based access affects not only security but also information architecture and user confidence.
  • Operational systems often need gating logic, such as payment confirmation, to enforce real business rules rather than just show status labels.

Design Strengths

  • Clear separation of admin, operator, and customer responsibilities
  • Readable dashboard organization and responsive layout
  • Practical workflow from appointment to work order to pickup
  • Strong validation on VINs, scheduling, and inventory-linked usage
  • Simple prototype architecture that is easy to demonstrate and extend

Limitations

  • No backend database or multi-user synchronization
  • No live payment processing or third-party messaging integration
  • localStorage-based persistence is suitable for prototype use but not enterprise deployment
  • Advanced analytics and enterprise reporting remain out of scope

Suggestions for Future Improvement

  • Migrate state persistence to a true backend and relational database.
  • Add invoice history, receipt export, and customer-facing billing history.
  • Support email/SMS notifications and multi-user concurrency.
  • Expand reporting dashboards and business analytics.
  • Introduce configurable technician skills, bay utilization reporting, and parts reorder workflows.

9. Conclusion

Torque Garage Public Prototype successfully delivers a realistic automotive service management workflow in a lightweight browser-based system. Although the final implementation is simpler than the original planned stack, it preserves the project’s core goals: organizing customer and vehicle data, improving appointment handling, tracking inventory use, enforcing role-based workflow, and validating practical repair-shop operations. The final system also demonstrates an important business rule that emerged during development: a vehicle should not be marked as picked up until invoice payment is confirmed. This makes the prototype a strong foundation for future full-stack development.

12. Appendix

Appendix A: Selected Pseudocode References

The following pseudocode summaries are adapted from the Phase I source-code document and are cited here because they influenced the final implementation approach for persistence, VIN validation, and form validation (Beo et al., 2026c).

Persistence pseudocode

Source: Beo et al. (2026c), state and persistence section.

1. Save the in-memory state object as JSON into localStorage.

2. Save authentication/session information separately.

3. On startup, attempt to load state from localStorage.

4. If no state exists or parsing fails, create demo state instead.

VIN validation pseudocode

Source: Beo et al. (2026c), VIN validation section.

1. Read the VIN value and normalize it to uppercase.

2. If empty, clear the VIN error and allow the form to continue.

3. If the VIN is not 17 valid characters and includes forbidden letters, mark the field invalid.

4. Show the VIN error message and block save.

Customer and vehicle form validation pseudocode

Source: Beo et al. (2026c), customer and vehicle validation examples.

1. Read required field values from the form.

2. If any required field is missing, show a form message and block submission.

3. If numeric values are invalid, show an error and block submission.

4. Clear the form message and continue only when validation passes.

13. System Specification

Technical Specifications

  • Frontend: HTML5, CSS3, Vanilla JavaScript (ES6+)
  • Persistence: Browser localStorage with JSON-backed record collections
  • Deployment Mode: Static browser-based prototype
  • Primary Files: index.html, style.css, script.js

Minimum Hardware and Software Requirements

  • A computer, laptop, tablet, or smartphone capable of running a modern browser
  • Chrome, Edge, Firefox, or Safari with JavaScript enabled
  • Sufficient browser storage for local demo data
  • No dedicated backend server required for the public prototype build
